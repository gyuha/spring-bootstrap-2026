# Lessons: Phase 5 (2026-05-31)

## Lens: Decisions/Surprises/Patterns/Mistakes
_Captured: 2026-05-31T13:45:00Z_
_Intent: capture technical decisions, unexpected outcomes, recurring techniques, and verification failures from this phase._

### Decisions
- D-01~D-07 고정: 신규 AuthController(MeController 무변경), 로그아웃 logout DSL 재사용 + HttpStatusReturningLogoutSuccessHandler(204), `/api/auth/logout`는 permitAll 제외(CSRF·인증 유지), returnTo는 세션 attribute("RETURN_TO") 방식 (05-CONTEXT.md)
- 리뷰 후 registration id 외부화: `/oauth2/authorization/test-idp` 하드코딩 → `@Value("${app.auth.oidc-registration-id:test-idp}")` — 베이스라인 재사용성 직결 (d001d1b, 리뷰 I1)
- AUTH-08/09/11(내 정보 신원·권한 집계)은 Phase 6로 명시 분리 — Phase 5는 집계 의존 없는 순수 인증 흐름만 (ROADMAP 분할)

### Surprises
- RESEARCH가 classpath 실측으로 "프레임워크 기본" 주장을 검증 — `HttpStatusReturningLogoutSuccessHandler`(6.5.1 존재), `UrlUtils.isValidRedirectUrl()`이 절대 URL 허용(자동 보호 없음) 확인. Phase 3 lesson("default 무검증 단언 금지")이 RESEARCH 단계에서 실제로 적용됨
- `isSafeRelativePath`가 역슬래시 우회(`/\evil.com`)에 뚫림 — 리뷰가 적발. 브라우저가 `\`→`/` 정규화(WHATWG URL)해 `//evil.com` open-redirect. 4-조건 검증의 사각이 코드 리뷰에서야 발견됨 (리뷰 C1)
- returnTo 세션 연속성(진입→authorize→콜백→successHandler)이 `changeSessionId` attribute 보존 덕에 첫 시도부터 GREEN — RESEARCH A1 가정이 실증됨(우려했던 BaselineOidcUserService 충돌 없음)

### Patterns
- types-first 선형 wave(SecurityConfig 인프라 → AuthController → 통합테스트) — 각 wave당 1플랜 엄격한 의존 체인. 병렬 0이라 순차 실행이 정답(sg-execute의 GROUP_COUNT≥2 자동 병렬 라우팅을 의존 체인 근거로 수동 우회)
- MeController의 `OidcUser.getAttribute("user_id")` 표준 읽기 계승 → infrastructure 타입 미참조로 ArchUnit interfaces→infrastructure 게이트 자연 통과(D-06). record + `@JsonInclude(NON_NULL)`로 Map.of NPE 정공법 회피
- SC 충실도: oidcLogin() 우회 금지, logout 204는 WireMock 실 토큰 교환 + `sessionRepository.findById==null` 서버측 read-back으로 단언(Phase 3 lesson 계승)
- 완료 단언 전 `./gradlew test --rerun-tasks` 독립 재검증 + 코드 전용 atomic commit(.planning 분리)

### Mistakes
- `isSafeRelativePath` 역슬래시 우회(리뷰 C1) — open-redirect 방지의 존재 이유를 무력화. 화이트리스트가 `//`·`://`만 막고 `\`를 누락. 교훈: open-redirect 검증은 backslash·URL 인코딩(%5C)·제어문자까지 회귀 테스트로 고정해야 함
- registration id `test-idp` 하드코딩(리뷰 I1) — 테스트 전용 값이 프로덕션 코드에 박혀 운영 로그인이 깨질 footgun. 재사용 골격에서 환경 종속 매직값 하드코딩은 Phase 1 `api.version` lesson의 재발
- 503 가드보다 RETURN_TO 저장이 먼저라 stale attribute 가능(리뷰 I2) — 실패 분기 전 부수효과(setAttribute) 배치 실수

### Action Items
| priority | item | next step |
|----------|------|-----------|
| 🔴 P1 | open-redirect 검증 헬퍼를 backslash·인코딩까지 막는 표준 형판으로 | sg-rule `warn-open-redirect-incomplete` 초안 — returnTo/redirect 검증에서 `\` 미검사 경고 |
| P2 | 환경 종속 매직값(registration id 등) 하드코딩 반복 방지 | Phase 1 `api.version` + 이번 `test-idp` 패턴을 게이트화 검토(설정 외부화 규칙) |
| P3 | 실패 분기 전 부수효과 배치 점검 | plan/review 체크리스트에 "guard 먼저, side-effect 나중" 항목 추가 |

# Lessons: Phase 6 (2026-05-31)

## Lens: Decisions/Surprises/Patterns/Mistakes
_Captured: 2026-05-31T14:35:00Z_
_Intent: capture technical decisions, unexpected outcomes, recurring techniques, and verification failures from this phase._

### Decisions
- D-02 권한 집계 = **direct only**(그룹/계층 상속 제외). 근거: `findEffectiveGrants(userId, resourceId)`가 resourceId 필수라 전체 열거 불가, effective 열거는 신규 CTE(범위 초과). 3버킷(roles/menus/resources) 구조는 유지해 향후 확장 가능. 한계를 PermissionView/MeResponse Javadoc + SUMMARY에 명문화.
- D-06 AUTH-11 = **ArchUnit 무변경 GREEN**. layered 규칙이 컨텍스트 무관 접미 글로브(`..interfaces..`→`..application..` 허용)라 교차 컨텍스트 호출이 이미 통과. IdentityLinkService(auth.application→identity.application) 선례. 컨텍스트 슬라이스 신설 안 함(simplicity-first).
- CQRS-lite read: 기존 쓰기 전용 application 서비스에 `@Transactional(readOnly=true)` 메서드 레벨 오버라이드로 read 추가. 도메인 타입(User/Email/RoleName)을 평탄 record DTO로 캡슐화해 interfaces 비노출.

### Surprises
- 기존 Identity/Authorization application 서비스에 **read 메서드가 0건**(전부 write)이었음 — 신규 read 메서드 필요. 도메인 포트엔 findByUserId/findById가 이미 존재해 추가는 modest.
- ArchUnit이 교차 컨텍스트 의존을 "우연히" 허용(컨텍스트 무관 글로브) — AUTH-11 "명시적 허용" 의도와 갭이 있으나, GREEN 단언 테스트로 충분(컨텍스트 슬라이스는 과설계).
- BffAuthMeIT가 BffAuthSessionIT보다 가벼움 — 모든 테스트가 oidcLogin() post-processor + 실 DB grant 시드라 MockOidcServer/WireMock 불필요(실 토큰 교환 불요). 신원은 실 User 조회를 단언해 거짓 통과 차단.

### Patterns
- types-first 선형 wave(DTO→application read→controller→IT) — 전방참조 컴파일 위험 0(Phase 4·5 계승).
- **시그니처 사전 실측**(findByUserId 3종, getRole/getMenuId, grant 메서드, RoleName 값) — 코딩 전 확인으로 Phase 4 "추정 시그니처" 리스크 회피. Wave 1·2 소스 수정 0건.
- 3자 일치 시드: invite 반환 실 DB PK = oidcLogin claim user_id = grant.userId. 합성 userId 하드코딩 금지(lesson 05).
- 완료 단언 전 `./gradlew test --rerun-tasks` 독립 재검증 + 코드 전용 atomic commit.

### Mistakes
- me()의 `((Number) principal.getAttribute("user_id")).longValue()` 무방비 캐스팅(리뷰 I-1) — user_id claim 부재 시 NPE→500(401이어야 함). **같은 코드베이스의 MeController가 이미 null-tolerant 선례**를 갖는데 일관성 회귀. Phase 5 C1(open-redirect 불완전)과 동일 계열 — "happy-path만 처리, 방어 누락"이 리뷰에서 반복 적발. `instanceof Number` 분기 + 401 테스트로 수정.

### Action Items
| priority | item | next step |
|----------|------|-----------|
| 🔴 P1 | controller 진입에서 principal attribute 접근은 처음부터 null/타입 방어(instanceof) | sg-rule `warn-unguarded-principal-attribute` 초안 — getAttribute 직후 무가드 캐스팅 경고 |
| P2 | "happy-path만 처리" 반복(Phase5 C1, Phase6 I-1)을 plan 단계에서 선제 차단 | plan 체크리스트에 "외부/세션 입력 경계는 부재/타입불일치 분기 필수" 추가 |
| P3 | AUTH-11류 "명시성" 요구가 무변경 GREEN으로 충족되는 경우의 판단 기준 | 슬라이스 규칙 vs 단언 테스트 트레이드오프 문서화 |
